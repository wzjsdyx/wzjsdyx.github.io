# 原文

> The QVN - QoS Virtual Networks (QVN-400) is the same concept as a resource plane. Grouping masters into different kinds of traffic classes or virtual networks can ensure that the masters on those different networks that can share wires and arbitration points in the system do not block each other. This function is achieved using buffers within the NIC-400, allowing transactions on different virtual networks to overtake each other. The main idea is that in a case where a memory controller is connected through a single input port, this port could easily be blocked by a particular set of masters. But the virtual networks ensure that a master cannot block it and that whichever virtual network can make forward progress will be able to issue transactions into the endpoint. As shown here, the output of the NIC-400 has a VAxQOSACCEPT input value, which goes from the slave back into the NIC-400. It is used by the slave to indicate how busy it is, so the more active the slave is, the higher the value. This value indicates that the NIC-400 should not present lower QoS value transactions than this VAxQOSACCEPT value driven back into the NIC-400. The main idea here is that you do not want, for example, the GPU to keep sending transactions and for the ASIB to keep trying to send them to the DMC when the DMC has little or no space available. We want to prioritize the masters with a latency intolerance because those masters still need to be processed first. So, in this example a value of 15 means only transactions with a QoS value of 15 will be allowed through (from LCD). A value of 12 means only transactions with a QoS value of 12 or higher will be allowed through (LCD and CPU) so GPU and VPU remain blocked.

# 原文翻译+图文理解

<font color=red>QVN（QoS Virtual Networks，服务质量虚拟网络） 是 QVN-400 提供的一项功能，其概念与资源平面（Resource Plane）相同。</font>

通过将不同的 Master 划分到不同的流量类别（Traffic Class）或虚拟网络（Virtual Network），可以确保即使这些 Master 共享系统中的物理连线和仲裁节点，不同虚拟网络之间的事务也不会相互阻塞。该功能通过 NIC-400 内部的 Buffer 实现，使不同虚拟网络中的事务能够相互超越（Overtake）。

其核心思想是：

假设一个内存控制器（Memory Controller）通过单个输入端口连接到 NIC-400，那么这个端口很容易被某一组 Master 的事务占满，导致其他 Master 无法访问。

但是，通过引入虚拟网络，可以避免某个 Master 长时间阻塞其他 Master。只要某个虚拟网络能够继续向前传输事务（Forward Progress），它就有机会将事务发送到最终目标设备。

如图所示，NIC-400 的输出接口上有一个 VAxQOSACCEPT 输入信号，该信号由 Slave 反馈给 NIC-400。

Slave 使用这个信号表示自身的繁忙程度：

- Slave 越繁忙，VAxQOSACCEPT 的值越大。
- VAxQOSACCEPT 表示当前能够接受的最低 QoS 优先级。
- NIC-400 不应该向 Slave 发送 QoS 值低于 VAxQOSACCEPT 的事务。

例如，我们不希望 GPU 不断发送事务，而 ASIB 又不断尝试将这些事务发送到 DMC（DRAM Memory Controller），因为此时 DMC 可能已经没有足够的空间处理这些请求。

我们希望优先处理那些对访问延迟更加敏感的 Master，因为它们的事务需要得到更及时的处理。

在本例中：

- VAxQOSACCEPT = 15：仅允许 QoS=15 的事务通过，例如 LCD。
- VAxQOSACCEPT = 12：允许 QoS≥12 的事务通过，例如 LCD 和 CPU。

因此，GPU 和 VPU 的低优先级事务仍然被阻塞。

# 原理解释

##  为什么需要 QVN？

假设系统包含四个 Master，共同通过 NIC-400 访问 DDR：

| Master | QoS  | 特点                   |
| ------ | ---- | ---------------------- |
| LCD    | 15   | 实时性要求极高         |
| CPU    | 12   | 对访问延迟敏感         |
| VPU    | 8    | 视频处理，带宽需求较大 |
| GPU    | 4    | 大量连续数据访问       |

不使用 QVN 时：

假设 GPU 连续发送大量事务，导致 NIC-400 内部 Buffer 被 GPU 的请求占满。

即使 LCD 的优先级最高，它的请求也可能被前面的 GPU 事务阻塞。

这就是 HOL Blocking（Head-of-Line Blocking，队头阻塞）。

![image-20261109194945460](D:\blog\wzjsdyx.github.io\source\_posts\2026-11-09-培训笔记-21-Extensions-QVN400\image-20261109194945460.png)

使用 QVN 后：

NIC-400 利用不同虚拟网络的 Buffer，允许 LCD 的高优先级事务绕过暂时无法继续传输的 GPU 事务。

![image-20261109194959177](D:\blog\wzjsdyx.github.io\source\_posts\2026-11-09-培训笔记-21-Extensions-QVN400\image-20261109194959177.png)

注意：QVN 并不意味着创建了多套独立的物理总线，而是通过 Buffer 隔离和调度机制实现逻辑上的虚拟网络。

## VAxQOSACCEPT 如何工作？

这是 QVN-400 中很关键的一个信号。

假设 DMC 根据自身繁忙程度动态调整 VAxQOSACCEPT：

| VAxQOSACCEPT | 允许通过的 Master  |
| ------------ | ------------------ |
| 0            | LCD、CPU、VPU、GPU |
| 8            | LCD、CPU、VPU      |
| 12           | LCD、CPU           |
| 15           | 仅 LCD             |

![image-20261109195030386](D:\blog\wzjsdyx.github.io\source\_posts\2026-11-09-培训笔记-21-Extensions-QVN400\image-20261109195030386.png)

这里需要特别注意：

VAxQOSACCEPT 不是直接控制某个 Master，而是限制 NIC-400 向对应 Slave 端口发送的事务优先级。

例如 DMC 繁忙时，设置为 12：

- GPU 的 QoS=4，不允许发送新事务。
- VPU 的 QoS=8，不允许发送新事务。
- CPU 的 QoS=12，允许发送。
- LCD 的 QoS=15，允许发送。

这样就把有限的 DMC 处理能力优先留给 CPU 和 LCD。

## QVN 与普通 QoS 仲裁有什么区别？

这是理解 QVN-400 最重要的地方。

| 对比项     | 普通 QoS 仲裁        | QVN-400                          |
| ---------- | -------------------- | -------------------------------- |
| 核心机制   | 根据 QoS 优先级仲裁  | 虚拟网络隔离 + QoS 控制          |
| Buffer     | 可能共享 Buffer      | 通过 Buffer 支持不同 VN 事务超越 |
| 队头阻塞   | 可能发生             | 可减少跨 VN 队头阻塞             |
| Slave 反馈 | 不一定具有           | 支持 VAxQOSACCEPT 门限           |
| 主要目标   | 优先选择高优先级事务 | 防止低优先级流量阻塞高优先级流量 |

举个核心区别：

普通 QoS 仲裁解决的是：

> LCD 和 GPU 同时申请资源，应该优先选择谁？

而 QVN 进一步解决的是：

> GPU 的请求已经排队，并且无法继续传输时，LCD 能不能绕过 GPU？

QVN 提供了这种跨虚拟网络的超越能力。

## QoS和QVN对写通道的影响

### 1. 最关键的限制：只能在 Burst 之间切换

假设：

- GPU：QoS=4，正在传输 256 Beat 的写 Burst。
- LCD：QoS=15，此时发起一个紧急写事务。
- 两者都访问 DMC 的同一个 AXI 写端口。

即使 LCD 的优先级最高，也不能打断 GPU 当前已经开始传输的 Burst。

它需要等待 GPU 当前 Burst 的最后一个 Beat 完成传输，才能获得 W 通道。

所以，QoS 不能实现 Write Burst 中途抢占，而 QVN 也不能突破这个限制。

### 2. 但有一个重要例外：QVN 扩展接口允许跨 VN 写数据交织

我进一步核对了 ARM 官方《QVN-400 Supplement》（DSU 0027F，第 2-2、2-3 页），发现需要纠正前面回答中过于绝对的一点：

当 NIC-400 接口向外扩展 QVN，并且事务属于不同 Virtual Network 时，QVN 协议允许不同写事务的 WDATA Beat 进行复用交织

例如：

```
VN0：GPU  A0 A1 A2 A3
VN1：LCD  B0 B1

普通 AXI4：
A0 A1 A2 A3 B0 B1

QVN 扩展接口（允许）：
A0 A1 B0 B1 A2 A3
```

但这需要接口支持 QVN 扩展，而不是仅仅在 NIC-400 内部启用 QVN。



### 3. 对你的判断作个更准确的总结

| 场景                         | 写操作的 QoS/QVN 效果                              |
| ---------------------------- | -------------------------------------------------- |
| 普通 QoS                     | 可以优化 AW 仲裁、请求速率，但不能中途抢占 W Burst |
| QVN 内部隔离                 | 可减少不同 VN 之间的队头阻塞                       |
| QVN 终止于普通 AXI4 DMC 端口 | WDATA 仍然不能跨 Burst 交织                        |
| QVN 扩展到外部接口           | 不同 VN 之间允许 Write Beat 交织                   |

所以，你提出的问题非常关键：QVN 能否显著改善写事务延迟，很大程度上取决于 QVN 在哪里终止。

如果最终 DMC 只有普通 AXI4 接口，那么你的判断基本成立：QVN 对 W 通道的实时抢占能力有限，但对 AW 排队和拥塞控制仍有价值。

如果 DMC 也支持 QVN 扩展，那么写事务就有机会实现更细粒度的调度。





# 总结

理解 QVN-400，抓住三个核心特性即可：

1. Virtual Network： 将不同 Master 的流量划分为不同虚拟网络，实现逻辑隔离。
2. Buffer Overtaking： 允许不同虚拟网络的事务相互超越，减少 HOL Blocking。
3. VAxQOSACCEPT： 由 Slave 反馈可接受的最低 QoS 门限，优先保障对延迟敏感的事务。

需要注意，QVN 并不能保证所有场景下绝对不阻塞。不同虚拟网络最终仍然共享物理带宽，实际效果受到 Buffer、仲裁和 Slave 处理能力的限制。

一句话总结：普通 QoS 解决“谁先走”，QVN 则进一步解决“前面的人走不了，后面的人能不能绕过去”。
